One document says what the app may do

The Czarter. Written by whoever is accountable for the app — the customer's admin or the SI.

PeopleWho signs in, with which identity provider, and whether MFA and a fresh login are required.
The agentThe service account it acts as, when it runs, what it may and must never do.
ConnectionsThe MCP servers, APIs and models it reaches — and exactly which tools.
ControlsLimits that refuse a call and holds that wait for a person's approval.

  limits:
    - id: max-stake
      description: Largest single bet
      server: playbook-wallet
      tool: place_bet
      field: stake
      op: "<="
      value: 1000
  holds:
    - id: live-bet
      reason: Bets on games in progress need approval
      when: { argEquals: { live: true } }
      ttlSeconds: 300

Czartup sets up the platform

Every step shows a dry run first, and every result is logged against the Czarter.

  1. Sign-in — creates the app in the identity provider (Auth0 today), with MFA for this app only
  2. Role and agent — the app's role and the agent's service account, with its external identity
  3. Grants — the agent may call exactly the listed tools, and nothing else
  4. Policy — limits and holds generated as policy, scoped to the app's namespace
  5. Verify — re-checks all of it against the live platform, step by step

Say “Build”

The coding agent works in a set order and stops where a person decides.

It builds any servers first, then the app, against gateway addresses only. Where a step belongs to the platform — registering a server, approving its tools, granting access — it stops and says exactly what the admin must do. It never scripts those steps: the agent writing the code is the party being governed, and it does not get to set its own limits.

Limits and holds are not in the code. The pack tells the coding agent to leave them out of the server. A refusal is the gateway's HTTP 403, and a hold is a 403 with an approval to wait for — so the checks prove Magertron™ enforced them, not the app.
